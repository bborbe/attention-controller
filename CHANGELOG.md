# Changelog

All notable changes to this project will be documented in this file.

Please choose versions by [Semantic Versioning](http://semver.org/).

* MAJOR version when you make incompatible API changes,
* MINOR version when you add functionality in a backwards-compatible manner, and
* PATCH version when you make backwards-compatible bug fixes.

## Unreleased

- fix: make "Other…" a real peer option inside a question's own option group, and have typing select it, so the state drawn on the board is the state that will be sent. The field used to sit *beside* the group, and `collectAnswers` discarded the checked pick the moment the box held text — the radio stayed filled on screen while the submission carried only the typed sentence, and the operator could not undo it, because a radio cannot be cleared once text exists. ⚠️ **The schema is untouched:** an answer is still exactly one of `option` / `text` / `skip`, which is precisely why the fix makes the pick visible rather than sending both. Typing clears every other pick on that card — on a multi-pick question, checking Other alone would leave the earlier boxes reading as picks that are never sent, the same defect one layer down. ⚠️ **The mirror holds too:** picking a named option after typing clears the text field, because the text WAS that option's answer. Left behind, the field would keep the old answer while the board drew the new pick, and `collectAnswers` reads text ahead of any pick — so the submission would carry the text the operator had moved on from. A question declaring no options keeps the bare field and renders no control at all, and the Other control carries `data-other` so it can never contribute a literal `"Other"` pick. ⚠️ The Other option's checked state is owned by the text field, never by a click anywhere on the option: a click on the option — its control or its `Other…` caption alike — is prevented and the field takes focus instead. ⚠️ The caption matters as much as the control, because the option renders as a `label` wrapping both: a click on the caption has the caption span as its target, so a guard keyed to the control alone would return early and leave the label's own activation to check it — the same defect, on the larger half of the target. A click could otherwise reach two states the submission drops — checked with an empty field (nothing is sent) and unchecked with text still present (the text is sent) — and on a single-pick card it would also take the operator's earlier pick with it, because a radio group releases the previous selection the moment another is checked and nothing restores it. ⚠️ `pkg/handler/attention-page.go` sat at 1995 of revive's 2000-line limit, so the 442-line stylesheet moved to an `attentionPageStyles` const in `attention-page-helpers.go` and is concatenated back into the template at the point it was cut from, so it still lands where it was cut from. ⚠️ That is a claim about the concatenation point, not about the bytes: the same change also edited the block it moved (`.option input` narrowed to `.option > input`, plus a new `.option .other` rule), so the served CSS is **not** byte-identical to the previous release. Five cases cover what had none: a positive no-options regression (the repo's only one — the two existing `class="other"` assertions are both negative), a pick-then-type e2e case asserting the **rendered DOM** (the stored answer is `text` on both the broken and the fixed build, so a stored-answer-only case would be green on the unfixed board), two click-inert e2e cases — one on a multi-pick card and one on a single-pick card — pinning that a click on the Other option, on its control and on its caption alike, neither checks it nor releases the picks already made, a keyboard case asking whether an arrow-key move onto Other is refused, and a **type-then-pick** case pinning the mirror order.

## v0.46.0

- perf: replace the task index's wholesale vault rebuild with a per-change incremental update. The watcher now hands `TaskIndex.ApplyPaths` the paths a vault change named, and the index re-reads exactly those files — one task-file write costs one file open and its own bytes, against the 6,057 opens and 61 MB a rebuild spent to learn the same fact. The safety net is no longer a timer-driven full vault rescan either: `TaskIndex.Reconcile` re-derives the index from a directory listing compared against the size and modification time of the files already held, reading only what moved, and re-reads the goal and topic rungs so a goal file added while the process runs still resolves. ⚠️ The tie-break between files sharing a `claude_session_id` is unchanged and is now applied in ascending path order over a path-keyed candidate set, so an incremental update and a full walk agree on the winner for every session — asserted by a spec that drives both to the same answer. ⚠️ `TaskIndex.Rebuild` is gone; `ApplyPaths` and `Reconcile` replace it, and the watcher drives both — `ApplyPaths` per drained event burst, `Reconcile` on the backstop window, because a dropped inotify event is the one change `ApplyPaths` cannot see. The now-misnamed `RebuildCount` follows it to `RefreshCount`. ⚠️ A reconcile takes a real copy of the serving maps rather than a reference before it walks: `ApplyPaths` mutates those maps in place, so reading the header past the lock is a concurrent map read and map write — a runtime fatal error, not a stale value — and a spec that overlaps the two writers now covers it under `-race`. A reconcile also refuses to install when an incremental update landed during its walk, so the older listing cannot discard it.

## v0.45.0

- feat: add `handler.NewBearerTokenHandler`, an HTTP middleware that admits a request only when it presents the configured token as `Authorization: Bearer <token>`, so the second, cluster-reachable listener can gate its business routes on the shared secret. A missing header, a malformed header and a wrong token are refused identically — same `401` status, same `{"error":{"code":"UNAUTHORIZED","message":"unauthorized"}}` body — libhttp's canonical `{error: {code, message, details}}` envelope, so a client needs no second parse path for this refusal — written through one `writeUnauthorized` helper — so the endpoint cannot be probed as an oracle for token validity. ⚠️ The comparison is `subtle.ConstantTimeCompare`, never `==`, because a byte-by-byte comparison leaks the token's prefix through timing. ⚠️ It fails closed: a handler built with an empty token refuses every request rather than admitting everyone, since the comparison alone treats an empty presented value as a match for an empty configured token. The token is a credential and is never logged — a refusal is logged by shape only (`token_present=%t`) — and never rendered. `factory.CreateBearerTokenHandler` is the pure-forwarding plumbing hook; wiring the middleware into the listener is a later change.

## v0.44.1

- fix: accept the arm's answer to a `permission` item after the board has already answered it, so a board click can no longer brick the gate. The store's `open -> answered` compare-and-set refused every second write, and the board's Allow / Deny carries no `resolved_by` — so the click consumed the item, the arm's own answer (the one that DOES carry a resolver, and the only shape the release path reads) was refused as `ALREADY_ANSWERED`, and the park could only run out its timeout with no path left to answer it. ⚠️ **The relaxation is scoped to `permission`, and to arm answers within it:** a second write is accepted only when the item is permission-class AND `resolved_by` is non-empty, so `message` and `ack` keep first-write-wins and the guard that stops a duplicate routing to `producer_id`. A second non-arm write on a permission item is still refused, and **an arm write cannot change the operator's verdict**: the verdict is preserved whenever one is already recorded, so a write carrying no `decision` — the field is optional on the request body — cannot erase the operator's denial, and one carrying the opposite verdict cannot flip an authorization gate's `deny` to `allow`. The arm's write on that path sets the resolver and leaves the **verdict** untouched — but it does re-stamp the answer's attribution (`answered_by`, `answered_at`, `answered_client`), so the record reads as the arm's write carrying the operator's verdict. The release path reads the resolver, not the attribution; preserving the operator's attribution on this path is a separate, deliberate decision and is not claimed here.

## v0.44.0

- feat: open a card body's links in a new tab, so following one no longer navigates the board out from under the operator. Every anchor `renderCardText` authors now carries `target="_blank" rel="noopener noreferrer"` — both the markdown-link branch and the bare-URL autolink. ⚠️ **The `rel` is not decoration.** `target="_blank"` on its own leaves the opened page a live `window.opener` that can navigate the board away, which is the exact harm the new tab exists to prevent; `noreferrer` additionally keeps the board's URL out of the target's referrer. ⚠️ **Scoped to anchors rendered from card body text.** The provenance line's task, goal and topic anchors are `template.URL` interpolations rather than `cardtext` output, and are deliberately unchanged — clicking a card's own task link is the board's navigation, not a jump out of it. Two spec files assert both surfaces, and the change was applied to the provenance literals by mistake first; they were reverted, which is what the `rel`/scope note here exists to keep from recurring.

## v0.43.0

- feat: render a markdown link in a card's body as a clickable anchor showing only its label, and autolink a bare `http(s)` URL. A card body is emitted as four plain `{{ … Payload }}` interpolations and one `Context`, and html/template escapes each as text — so `[pane 87](http://127.0.0.1:1337/jump?pane=87&t=…)` reached the operator as literal characters, the whole URL visible and nothing clickable, on `review:` cards the operator is expected to act on. ⚠️ **The escaping boundary moves, and that is the risk.** The body now passes through `renderCardText`, which returns `template.HTML` — the only way an anchor is representable at all — so that function, not the template, owns escaping. Its contract: every byte reaches the output either `html.EscapeString`'d or inside markup it authored, and the one value reaching an attribute has had its **scheme checked by name** against a closed allowlist (`http`, `https`, `obsidian`) before becoming trusted. A denylist was rejected as the shape: it must enumerate every dangerous scheme and is wrong the first time one is missed. `javascript:` and `data:` render as their own escaped text, with no anchor. ⚠️ **A cut mid-link is suppressed rather than half-rendered.** The producer stores a payload at a fixed length, so a body can arrive as `[pane 88](http://127.0.0.1:1337/` — a real URL behind broken link syntax. Autolinking that fragment would point the operator at a 404 while looking correct, so a bare URL immediately preceded by `](` is emitted as text: an unclosed `](` suppresses both the anchor and the autolink. ⚠️ The four `Payload` sites and the one `Context` site were each wired individually; fixing only the `.payload` div would have left the record, card-title and question-panel bodies rendering raw. ⚠️ **Four producer-controlled fields are deliberately NOT wired:** `.Record` (the operator's own answer echoed back), `$question.Hint`, `.option-label` and `.option-desc`. All four remain html/template-escaped, so this is a consistency gap rather than a hole — a producer that puts a link in an option description still sees literal markdown. They are left alone because a link is not wanted in an echoed answer or a pick-list button label; `.option-desc` is the one arguable case and is a separate decision. Expected hrefs in the specs are hand-written literals, never built with the same escaper the code uses, which would agree with itself whatever it produced.

## v0.42.1

- perf: read each producer's event log from a remembered byte offset instead of re-scanning it whole, so a render over an unchanged log performs no read at all. `readEvents` in `pkg/provenance.go` now keeps a `producerEventLog` per producer — the byte offset it has consumed and the records those bytes decoded to — and returns the accumulated events unchanged when the log's size still equals that offset; only the bytes beyond it are read and decoded, so the work is proportional to what was appended rather than to the whole log. The read sits behind an injectable `EventLogReader` seam (`pkg/event-log-reader.go`, `Size` and `ReadFrom`) rather than a bare function, so the no-read case is observable: a spec wraps the real reader in a counting fake and asserts a second render reads nothing. ⚠️ The offset advances by READING the file, never by waiting for a notification or a timer, which is what preserves the freshness guarantee — a just-appended line is visible to the very next render, because the render stats the file and reads whatever lies beyond the offset. ⚠️ It advances by the bytes actually consumed — the index of the last newline plus one — never by the file size: a torn final line lies beyond the last newline, is left unconsumed, and resolves exactly once when it completes. A log that shrank below the remembered offset was truncated or replaced, so it is re-read from the start rather than misread from the middle; an absent or unreadable log proves nothing and leaves the accumulated events as they stand. The reader reads in binary rather than through a text handle, because a text-mode offset is only correct while every line is pure ASCII. The resolver no longer holds the state directory itself — it is handed the reader, so a host with no event-log source is a legal configuration.

- perf: keep the vault task index current with a filesystem watcher instead of a per-lookup refresh window, so a task created while the controller runs resolves its provenance without a restart and without re-reading the vault on a timer. `pkg/task-index-watcher.go` watches `<vault>/25 Tasks/` through a new direct dependency `github.com/fsnotify/fsnotify` and coalesces the events already queued into a single `TaskIndex.Rebuild`; the two-second `taskIndexRefreshWindow` per-lookup rebuild in `pkg/provenance.go` is replaced by a five-minute `taskIndexBackstopWindow`, so a missed watcher event self-heals rather than being the only refresh path. ⚠️ The queued events are drained before the rebuild rather than rebuilt one-per-event: a rebuild reads the whole vault, so an obsidian-git autocommit or a `git checkout` touching hundreds of task files would otherwise cost one full-vault read per file — the same pathology this change exists to remove. `main.go` builds one index and hands the same instance to the resolver and the watcher — two indexes would be two independent maps that could disagree about the same session — and the watcher is started and stopped with the service, closed by defer so a cancelled context leaves no inotify watch behind. Every failure is fail-soft: a watcher that cannot be created, or whose task directory cannot be added, logs a warning and returns nil, leaving the service serving and the backstop converging — a watcher failure must never take the process down. ⚠️ The watch set is exactly one directory: the index reads the goal and topic rungs too, but those change rarely and the backstop covers them, and widening the watch set would let the watcher's scope drift from the index it serves. The index's soft-failure rules are unchanged — the rebuild is single-flight and installs only when the task walk actually read `25 Tasks/`, so a cancelled or failed rebuild leaves the previous index serving, and an empty vault, a missing vault and an unreadable `24 Goals/` or `23 Topics/` all degrade exactly as before.

## v0.42.0

- fix: enforce `expires_at`, so an item past its own declared deadline is removed on read. The field was written at push and read nowhere — no comparison against the current time existed anywhere in the repo — so a deadline bounded nothing, which stayed invisible only while producer liveness pruned every ask within minutes. It stops being invisible with the `owner:<id>` model: that model is deliberately never pruned by a liveness probe, so an item carrying it was genuinely unbounded, and the marker that fixes *"gates vanish before they are answered"* would have traded it for *"gates never vanish"*. `classifyForRead` now checks expiry **before** the liveness probe, so an expired item is removed however alive its producer or its owner reads; an item declaring no `expires_at` does **not** expire, which is the schema's default — persistence is what an unanswered ask gets unless its producer declares a deadline. ⚠️ **The prune's re-check had to learn expiry too, and that half is the one that actually deletes.** `pruneDead` re-checks liveness before removing, because liveness is not monotonic — but expiry *is*, and for an `owner:` ref the liveness probe returns a constant `true`, so an expired owner item left behind that check was **hidden from the board while its row survived**, ready to be resurrected by the next dedup re-push. The check is now expiry-first (and renamed `stillRemovable`, since only one of its two causes is death). A first cut of this change asserted only that the board stopped rendering the item and passed while the row was still there; the specs now assert `store.Get` as well. ⚠️ `History` also skips an expired **open** item — its one narrowing, since such an item is neither what resolved nor what escalated; answered and closed items are untouched. Both write paths refuse a zero `expires_at` — `PushRequest.Validate` and `Item.Validate` share one rule — because a guard on the stored item alone left the dedup re-push path (`updateExistingIfLive`, which never validates) able to store the zero instant unchecked, and a row carrying it is deleted on the next read. ⚠️ **Upgrade note:** a row persisted before this change that carries a serialised zero `expires_at` was inert then and is subject to enforcement now, so it will be removed on its first read. The population is narrow — only producers that explicitly sent `0001-01-01T00:00:00Z` — and removing such a row is the correct reading of the field, but it is a behaviour change rather than a pure addition. `Push` now validates its own request rather than trusting the caller, so the rule cannot be half-armed by a future non-HTTP caller. ⚠️ **A History consumer that counts must now walk faster than the expiry horizon, or pin a cutoff:** the narrowing is a wall-clock predicate applied to an offset-paginated walk, so a row can stop being reachable partway through and every later row shifts one position earlier. ⚠️ **This supersedes the caveat in `v0.41.0` below**, which recorded the gap rather than papering over it; that entry is left as written because it was accurate when its tag was cut. Declared on `[[Attention Item Schema]]` § Lifecycle → *Expiry*.

## v0.41.0

- feat: add the `owner:<id>` liveness model, so an operator gate posted by a worker survives the worker's exit. The read path removed any item whose producer had exited and whose `answer_mechanism` was not `ack` — which is exactly a worker-posted operator gate, since a headless worker is *supposed* to end its turn, so the question left the board before the operator could answer it. `OwnerLivenessModel` is a third **model** and **not a second probe**: it resolves against nothing. ⚠️ **It never prunes on liveness, deliberately:** the registry deletes an entry on exit, so *never registered* (a human owner, a supervisor with no session row) and *exited* are the same signal — and reading either as gone would prune the very gate this model exists to keep, one layer in. An `owner:` item is therefore **not bounded by a probe at all** — it survives until it is answered or closed. ⚠️ **`expires_at` is not a bound either: nothing in this repo compares it to the current time**, so the field is written at push and never read. That is a pre-existing gap, recorded separately rather than papered over here — an earlier draft of this entry called `expires_at` the bound, and it is not. `classifyForRead` is unchanged, and a `session:` or stale-`heartbeat:` item is still pruned exactly as before. Declared on `[[Attention Item Schema]]` as silence 27 before this landed, per `CLAUDE.md` § Schema discipline.

## v0.40.1

- fix: keep a failed task-index rebuild from wiping the index, so a rebuild whose `25 Tasks/` read fails no longer replaces a fully resolved index with an empty one. The build fails soft on I/O, so an unreadable tasks directory yields no entries and no error — which made the empty result indistinguishable from a genuinely empty vault, and the refresh installed it. `readTasks` in `pkg/provenance.go` now reports whether it actually read the directory, and `refreshIfStale` installs a rebuild only when it both completed and reported that read: a cancelled rebuild and one whose task walk could not read `25 Tasks/` both leave the previous index serving. ⚠️ A failed `24 Goals/` or `23 Topics/` read is deliberately NOT such a signal — those rungs degrade to no goal and no topic by design, and refusing the install on them would block a good task walk, including the ordinary case of a vault with no `24 Goals/` at all. ⚠️ A refused install does not advance `builtAt`, so the window stays lapsed and the next `Lookup` re-attempts the rebuild rather than needing a retry loop; the cost is that a permanently unreadable `25 Tasks/` re-runs the goal and topic rungs on every lookup. The boot build in `NewTaskIndex` is still installed unconditionally, because at boot there is no previous index to preserve.

- fix: refresh the vault task index after boot, so a task created while the controller runs resolves its provenance without a restart. `pkg.NewTaskIndex` read the whole vault once at construction, so every task file written afterwards was invisible for the process's lifetime and its session rendered no task, goal or topic. `pkg/provenance.go` now rebuilds the index at most once per `taskIndexRefreshWindow` (2 s), driven by an injected `libtime.CurrentDateTimeGetter`, and `Lookup` stays a map hit on the common path. The rebuild re-runs all three index steps — goal titles, goal topics and the task walk — into a FRESH index whose maps are swapped in under a `sync.RWMutex` only once the whole rebuild has completed AND its task walk actually read `25 Tasks/`, so a cancelled rebuild — or one whose tasks directory could not be read — leaves the previous index serving rather than replacing it with an empty one; every documented soft-failure rule (empty vault, missing vault, unreadable `25 Tasks/`, `24 Goals/` or `23 Topics/`) is preserved. The refresh is single-flight, mirroring `provenanceResolver.hostState`: the staleness check and the token claim happen in one critical section, so a burst of concurrent `Lookup` calls that all observe a lapsed window — `Lookup` is reached once per item from the resolver's render loop — triggers ONE rebuild rather than one full-vault read per render, the winner rebuilding synchronously while the others are served the index already installed. ⚠️ `NewTaskIndex` gains a `libtime.CurrentDateTimeGetter` parameter, so every call site passes one.

## v0.39.3

- fix: give the prune its own session-liveness snapshot, so the read's compare-and-delete re-check answers against the value that is live NOW instead of the snapshot the disposition came from. `read` threaded one `readSessionLiveness` through both `classifyForRead` and `pruneDead`, so the prune's re-check read the same listing the classification used — and a re-check that cannot disagree with the verdict that produced it is a no-op, silently removing the protection against deleting an item whose session resumed in the classification→prune window, the "live now" contract the ⚠️ comment above `pruneDead` states. `pruneDead` now builds its own `readSessionLiveness` over the same checker and resolves it BEFORE its `Update` opens — resolving lazily inside the callback would hold the writer lock across a whole registry listing, the lock-hold the read split exists to avoid — while `classifyForRead` keeps the read's source, so a read lists the registry at most twice whatever the open-item count: once for classification, once for the prune. A read that prunes nothing still returns early and lists nothing extra. The pruning spec in `pkg/read-liveness-count_test.go` moves from 1 to 2 consults, because the prune re-lists once and shares that one listing across all re-checked items.

- perf: list the session registry once per board read instead of once per open item, so a read's cost stops scaling with the number of open items. Every `classifyForRead` and every `stillDead` re-check called the session-liveness checker directly, and each call opened `~/.claude/sessions`, listed it with `Readdirnames` and decoded its entries — a cost paid again by every connected stream on every store change. `pkg/session-liveness-checker.go` gains a one-listing `LiveSessions` capability and a per-read `readSessionLiveness` source that takes a single snapshot LAZILY on the first session lookup and answers every later lookup from it, so a read that tests no session-model item lists nothing. The read threads that one source through `classifyForRead`, `pruneDead` and `stillDead`, while the push path keeps the checker directly. ⚠️ `LiveSessions` is deliberately NOT added to `SessionLivenessChecker`: a zero-value Counterfeiter fake would report "unreadable", which reads as everything-is-live and would silently disable pruning in the 25 test files that inject one — so it stays a separate capability the real checker satisfies, and every injected fake keeps working through the fallback. The unreadable-registry-reads-as-live rule is unchanged.

## v0.39.2

- fix: reconnect the board's live stream when `EventSource` abandons the connection, so a terminal stream failure no longer strands an open board behind its not-tracking state until a manual reload. ⚠️ **`EventSource` re-establishes a network drop but not a response it treats as fatal** — a non-200 status, or a body whose content type is not `text/event-stream` — and the stream handler produces exactly that shape when the baseline render fails, because it sets that header only after the render succeeds: `ServeHTTP` returns before `resp.Header().Set("Content-Type", "text/event-stream")`. `EventSource` then goes `CLOSED` and never asks again, while the page's `onerror` only unhid the not-tracking span and its comment asserted the reconnect it was relying on — so the state could never be cleared, because no frame was ever coming. `pkg/handler/attention-page.go` now builds its stream in a `connect()` whose `onerror` reconnects **only when `source.readyState === EventSource.CLOSED`**, the case `EventSource` abandons, with a bounded exponential backoff (1 s doubling to a 30 s ceiling, reset on `onopen`); the `CONNECTING` case is left to `EventSource`'s own retry, and the not-tracking indicator keeps its semantics exactly — shown by `onerror`, cleared by the next **frame**, never by a reconnect. ⚠️ **Measured 2026-10-04, real binary in a real browser:** a `500`, and a `200` carrying `text/plain`, each cost **one** stream request and produced **no** recovery across 59 pushes over 30 s, while a plain restart recovered on its own in about 3 s — which is why a restart cannot exercise this defect and why the new e2e case is not a restart case. After the fix the same probe measures **5** requests and recovery. The e2e case *"recovers when the stream returns a response that is not an event stream"* is RED on the pre-fix revision — it times out on the request count, the assertion the existing abort case can never make, because there the retry is `EventSource`'s own — and GREEN on the fixed one; the abort case is kept unchanged as the retryable-path regression.

## v0.39.1

- fix: bound the history read, which returned the whole store on every request. `GET /api/1.0/attention/history` was `store.Map` over the entire items bucket — no filter, no limit, no pagination — so it decoded and serialized all **22,381** rows (**18.77 MB**, measured 2026-10-04) including the ~19,500 closed ones, and it did so on every call. It now takes `?limit=` and `?offset=` and returns items **newest-first**, defaulting to 1000 rows (~0.8 MB); `limit=0` is the unbounded compatibility path for a caller that genuinely needs the whole store, so what changed is that a caller has to ASK for everything rather than getting it by default. ⚠️ **The ordering is the half that makes the bound mean anything, and it is why this needed an index rather than a cursor.** Item ids are random 128-bit hex (`item-id-generator.go`), so items-bucket key order carries no time meaning — a `limit` over it would have returned an ARBITRARY 1000 rows that shifted as the store grew, and the endpoint's consumers count resolutions across the whole store, so an arbitrary page is worse than no page. A new `attention-history-index` bucket keys every item by creation time (the third derived index, maintained by the same `reconcileIndexes` and rebuilt by the same `rebuildIndex`, both generalised to take a key function so `dupl` does not get three near-identical copies), and `History` walks it with `IteratorReverse`. ⚠️ **That key can MOVE, and the reconciler removes the old one when it does.** It is derived from `CreatedAt`, and `CreatedAt` is **rewritten** by `updateExistingIfLive` on a duplicate-suppressed push — so the same item is legitimately written under two keys, while the history index's constant-`true` predicate means `reconcileIndex` would otherwise only ever ADD. Without the removal the index strands one entry per suppressed push and `History` returns the same item once per push, defeating the counting purpose the endpoint exists for. **This was caught in review, and the thing it caught was a comment rather than a line of code:** the comment defending the key as stable asserted that `CreatedAt` "is written once and never rewritten", which is false at `updateExistingIfLive` — the design rested on an unverified assumption about a field's immutability, and the spec that reproduces it has to build the index *before* the suppressed push, because the first `History` read performs the one-time rebuild whose second pass silently cleans the orphan. ⚠️ **The key layout is fixed-width for a reason worth recording:** `time.RFC3339Nano` TRIMS trailing zeros, so `…:37Z` and `…:37.1Z` sort with 37.1 BEFORE 37 — `.` is 0x2E and `Z` is 0x5A — and the index would have returned a "newest-first" page that was not newest-first, silently, and only for rows whose timestamps fell on a whole second. Nine fixed digits removes it. The item id is appended after a separator so two items sharing a nanosecond stay distinct. ⚠️ **`removeItem` now reads the item before deleting it**, because the history key is `created_at|id` and the id alone cannot locate the entry; when the item is already gone the entry is left for the rebuild rather than guessed at, since a wrong key removes nothing and reports success. ⚠️ **The response stays a bare JSON array** — the REST guide records that a pagination envelope is not yet standardized and should not be invented silently — so consumers that count must walk the pages rather than read one. ⚠️ The three known callers of this endpoint — `attention-latency.py`, `attention-stuck-card.sh` and `tests/attention-closer-echo-roundtrip.sh` — live OUTSIDE this repository (under `~/.claude/scripts` and in the vault), so this repo cannot ship them; they are updated alongside this change rather than by it.
