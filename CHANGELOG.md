## v0.23.2

- feat: render the corner X on `permission` rows too, removing the last exception. The operator asked for the X on *"each card"* and the `permission` exclusion was never their ruling — it was read off a `y` on a manager's menu option (*"X on every card except permission"*), and the operator has since disowned it verbatim: *"Sorry, this was not my intention. I want it on every card without any excludes."* So the `y` was assent to a menu they did not write, and the ask's literal form was accurate all along. ⚠️ **The X on a `permission` card CLEARS it without ANSWERING the gate, and that distinction is the whole change.** The earlier reading held that any control there *"would be the permission laundering the schema forbids"* — which conflated answering with clearing. The X posts `/close`, writing `open` → `closed` with `answered_at` and `decision` both unset and **no answer routed**, so the asking session stays **frozen and waiting exactly as it was**; the gate is still answered only by the operator, in the session that raised it. ⚠️ **The real consequence is exposure, not laundering, and it is recorded rather than waved away:** clearing a card removes it from the board **while the gate still waits**, and the board is the only surface showing that gate — so a scripted click could now **hide** a permission gate rather than answer it. That is a new site in the same family the `answered_client` census covers, and it is handed to [[A Scripted Browser Click Is Indistinguishable From the Operator's Own]] rather than half-fixed here. ⚠️ **Schema first**, per `CLAUDE.md` § Schema discipline: [[Attention Item Schema]] is amended in **seven** places before this code change — the Lifecycle `open` → `closed` row, the control-set table's `permission`/`open` row, the § *The corner X* paragraph **and** its per-mechanism table row, the two boundary sentences still reading *"a `permission` card is untouched"*, silence 20's restatement of the old bound (*"including no corner X"*), and the census pointer. The three the task named were not enough — each of the other four asserted the exception independently, so amending only those three would have left the page contradicting itself. ⚠️ **The gate is unconditional, not `{{if or .Message .Ack .Permission}}`** — v0.23.1 deleted the `Permission` row field, so there is no field to read, and a fourth mechanism inheriting the X is now the consistent outcome rather than a leak. ⚠️ **The dispatch gains no branch:** a `permission` row carries no `form.answer`, so it already falls through to `closeCard` exactly as an `ack` row does; only the comment claiming otherwise was rewritten. ⚠️ **That function is renamed from `closeAck` in this same change** — it now serves a permission card's X as well as an ack card's Acknowledge, so the ack-flavoured name misdescribed one of its two callers, and its hardcoded *"Acknowledged."* was wrong for the other. The note's verb is now read off the row. ⚠️ **Four specs asserted the old behaviour and are amended rather than deleted** — the inverted negative control in `attention-page_test.go`, which now asserts a permission row **carries** the X so a regression that re-excludes it fails, and three in `attention-board-page_test.go` that used `NotTo("<button")` as a proxy for *"carries no control"*. That proxy is now wrong for the **second** time (the jump corner broke it once, the X breaks it again), so it is replaced by the ANSWER-control markers (`data-ack`, `<form`, `<input`) — the property those specs were always about.

- fix: stop a list read from holding a write transaction across its whole scan, so it no longer starves every Push behind it. `read()` opened `db.Update` — a **read-write** transaction — and held it across a scan that JSON-decodes **every** item *and* runs a per-item liveness check that does file I/O (an `os.Stat`, or up to **70** uncached session-registry reads). bbolt permits one read-write transaction at a time, so every list read blocked every other read *and* every write for the length of that scan. Measured 2026-09-27 against the deployed store: `/api/1.0/attention` answered in **`0.03 s`** when quiet and **`10.6 s`** under load, `attention-ask.py post` failed on **every** attempt with `attention store unreachable … (timed out)` because a valid write could not get the lock a read was holding, and the process sat at **`46–82 %`** CPU decoding items it held a writer lock over — a blocked *waiter* burns no CPU, the *holder* does, which is why two readings of the same defect disagreed (`6.4 %` early, `67.1 %` later). It is now three short steps: a `View` that only decodes, taking **no** writer lock and so unable to starve a Push; classification, with its per-item liveness I/O, **outside every transaction**; and a short `Update` that prunes dead items **only when there are any**, so the common healthy read is read-only end to end. ⚠️ **The prune is a compare-and-delete, not a blind delete — and the first version of this change got that wrong.** A `remove` disposition is computed from a snapshot, and two independent things change after it is taken. The item's **state**: `Answer` and `Close` take no liveness gate, because an answer may legitimately name an item whose asker is gone, so an item classified dead while open can be answered before the prune runs — and deleting it rewrites history the schema says is never rewritten. The producer's **liveness**, which is **not** monotonic: a refreshed heartbeat file, a session resumed under the same id, or an unreadable registry (which reads as live) each flip a producer back, and `updateExistingIfLive` then updates that item's key in place. ⚠️ **Both were reproduced against the first version** — an answer landing inside the classification window left the item gone from `History` entirely, and a live producer's just-refreshed item was pruned. The old single-transaction read could not hit either, because `Answer` needed the same write lock and serialized behind it, so the split introduced the window. `pruneDead` now re-reads state **and** liveness against the live value inside its own transaction — the repo's own rule that a compare-and-set belongs inside the transaction, never a separate read then write — while the scan itself still runs outside every transaction, which is what the split was for. ⚠️ **Four specs pin this, and all four were verified to discriminate rather than merely to pass.** Two pin the transaction *shape* — a healthy read opens **zero** write transactions, a prune opens **exactly one** — and go red when `readItems` is reverted to `Update` (`0 Passed | 2 Failed`). Two pin the prune's *safety*, one per axis above: an item answered mid-window and an item whose producer came back mid-window must both survive. ⚠️ **Those two go red when the prune is reverted to a blind delete (`2 Passed | 2 Failed`) while the shape specs stay green** — which is exactly the gap that let the first version ship: counting transactions says nothing about what the prune removes. ⚠️ **This fixes the read path's own saturation only.** The board page and the stream additionally resolve provenance per render, which spawns `wezterm cli list` as a subprocess and re-reads the whole session registry and the producers' event logs; that cost is untouched here and is a separate change.

## v0.22.0

- feat: carry the board's filter in the URL, so a reload, a bookmark or a shared link reproduces the filtered view instead of resetting it. The operator asked for it while reviewing the switch: *"The hide button at the top should be a URL parameter, so a reload of the page keeps the preview setting."* ⚠️ **The premise it arrived with was wrong, and the difference changed the shape of the change.** It was relayed as *"the page already reads `text` and `kind` for the answer form, so the mechanism is on that page already"* — it does not. The page read **no** query parameter at all: no `URL.Query()` on the Go side, no `URLSearchParams` on the script side, and the answer form carries no `method` or `action` because the script handles it. So this adds the page's **first** query parameter rather than extending an existing mechanism, which is why it is verified as a new one. The parameter is `hide=answered`, and its value names the **set that is hidden** rather than being a boolean, so the URL reads as an instruction and a later view can be described without a second parameter name. Three properties are load-bearing. **The server renders the switch's initial position from the parameter** while the script reads the same one to apply the filter, so the served markup agrees with the URL the operator is looking at; those two readings are the only thing in this file that exists in two languages, and a spec asserts both halves. **The hidden rows are still served** — a server that dropped them would make the switch one-way, which is the opposite of what a view filter is. And **the URL is written with `replaceState`, not `pushState`**: the filter is a view, and a view that filled the Back stack would make Back mean *undo my filter* on some presses and *leave the page* on others, while with no `popstate` handler a pushed entry would also leave the URL and the page disagreeing after a Back. It changes the URL without a navigation, so the no-reload property the switch already had is intact.

## v0.21.0

- feat: restyle the board's answerable filter as a **switch** rather than a button, on the operator's own click-through of `v0.20.0` — *"works .. but a ugly button ... maybe a svg like this"*, with a reference image of a pill switch. A button was the wrong shape for what the control is: a two-state view control that stays where it is, not an action that fires and returns. The control is now an inline SVG pill — a track carrying the state in colour and a knob carrying it in position, so "on" is legible from the page itself rather than only from the wording. The knob stays light in both states, as the reference does, and only the track changes colour, taking the same affirmative pair (`--green-bg` / `--green`) the card's Submit answer already uses rather than adding a colour to the palette; geometry and palette are both reused rather than invented, per the page's own base block. ⚠️ **The visible label is kept beside the switch, which is a deliberate rejection of the obvious reading of the reference.** The image is a bare switch, and an unlabelled one here would repeat the mistake `v0.18.0` recorded for the read-aloud control — moving a control's meaning into a hover-only `title` plus an `aria-label` only assistive tech sees, on a board whose governing complaint was cards *"whose controls were not discoverable at all"*. The switch carries the **state** and the label carries the **meaning**; a spec pins both. ⚠️ **The semantics changed with the shape:** the control now carries `role="switch"` with `aria-checked` instead of `aria-pressed`, which is the shape a two-state control is meant to have — a control reporting both would tell assistive tech two different things about one state, and the spec asserts `aria-pressed` is absent. The CSS ordering is load-bearing as well: the on-state rule is written after `:hover` deliberately, because the two have equal specificity and source order is what stops the state colour being flattened by the pointer.

## v0.20.0

- feat: add a toggle at the top of the attention board that hides the dimmed answered record cards, so the board answers *what is left* instead of showing records beside open prompts. The operator asked for it verbatim, looking at the live board: *"The idea is that I have a toggle that only shows the card where I can still answer something, so I see left items."* The control is the board's own view — it renders no item, writes no field and causes no transition, so it adds no row to the schema's control-set table and no state to § Lifecycle. Two properties are load-bearing rather than cosmetic. **A filtered row is removed, not hidden:** a `display:none` rule leaves the node in the document, where a selector, a script or the operator's own assistive tooling still finds a card the board claims not to be showing. **And the filter runs on the live-stream path, not only at first paint:** the channel sends an already-rendered row and the page swaps it in, so a filter that ran once at load would leak every row that arrived afterwards. Hidden rows are parked as their rendered HTML plus the id of the row that followed, and restored **back to front** — parking a run of adjacent dimmed rows records each one's anchor as the next, so a forward restore would find none of them yet and drop the whole run at the foot of the board. A row that streams an update while hidden updates its parked entry **in place** rather than being re-parked: it is not in the document at that moment, so the lookup misses it, and appending it would record a fresh anchor of `null` — bringing the record back at the foot of the board, which is the failure the anchor exists to prevent. A row the store removes while parked is dropped from the parked set, so it cannot come back when the filter is switched off; the filter is wired above the `EventSource` guard, because a browser with no SSE still renders the board and still has to be able to ask what is left; and the empty-state collapse declines to fire on a list the filter emptied, since that list is where the parked rows restore to. ## v0.17.0

- fix: clear the write deadline on the board's live stream, so the server stops killing it every 30 seconds. `libhttp.NewServer` sets a 30-second `WriteTimeout` by default and this repo never overrode it, and a write deadline is fatal to a stream: once it passes, the connection is killed mid-response, the browser reports `ERR_INCOMPLETE_CHUNKED_ENCODING`, and `EventSource` silently reconnects. The board therefore *looked* like it worked while dropping and re-establishing the channel every 30 seconds — and it would have satisfied a restart-and-reconnect criterion for the wrong reason, because reconnection was happening constantly anyway. Found by the end-to-end pass against the deployed service and by no unit spec: `httptest`'s default server sets no write deadline, so every existing spec passed whether or not the handler cleared one, because the defect is a property of the server the handler runs under rather than of the handler's own logic. The deadline is cleared per response via `http.NewResponseController`, not by raising the server's `WriteTimeout`, which is shared by every route and would remove a real protection from the handlers that do finish. The new spec runs the handler under a deliberately short deadline and asserts an event still arrives past it, and it was verified to **fail** with the fix removed — a real check rather than a decorative one.

- feat: keep an answered board card on the board as a **dimmed record** carrying the answer the store recorded, and remove it only when the item reaches `closed` — instead of the card vanishing the moment it was answered. The board's purpose on this stack is resolution rather than delivery, and a card that disappears the instant it is answered reports *that* something left the queue while withholding *what was decided*. The load-bearing argument is evidentiary: `answered_by` is a **caller declaration**, so a human click and a page-driven POST write the identical value, and a card that vanished on answering destroyed that record at exactly the moment the operator could notice it was wrong. The board reads through a new `ReadBoard`, which returns the open items **plus** the `answered` ones; the JSON read API keeps calling `Read` and its payload is unchanged, because its consumers act on what they are given and must not be handed an already-answered item. `closed` items stay absent from both. The shared prune is deliberately **not** widened: an answered item is classified before the producer-liveness check and is never removed, which the schema requires because its history is never rewritten — a spec pair proves both halves, an answered item from a dead producer surviving while an open asked item from a dead producer is still removed in the same pass. The record renders per answer kind from the field the schema names — `answer` for a `message` item, `answers` one line per tab for a multi-question item, `decision` for a `permission` item, and a `skip` marker rather than an empty string, which would be indistinguishable from an answer that failed to load. The schema is amended first, per this repo's § Schema discipline: the control-set table's `answered` / `closed` row is split and a § The dimmed record card section carries the content matrix

## v0.16.0

## v0.13.0

- feat: make the attention board update in place, so a new or resolved item reaches an open board without the operator reloading it. The page carried **zero automatic refresh mechanisms** — `EventSource`, `setInterval`, `setTimeout` and `http-equiv="refresh"` each appeared 0 times in the served document — so a tab left open showed the card list exactly as it was at load, and the cost was not hypothetical: an operator working a list that went stale had a card mutate underneath them and neither side could attribute the click.
