## Summary

- The board withholds the **Allow / Deny** pair on a headless worker's `permission` card when the item's **own task file** declares a production-touching step — the item's park is irreversible, so a one-click board approval is the harm this excludes.
- The signal is the operator's **authored** marker on a task's own subtask line (`- [ ] ⚠️ production-touching — <command>`), not a guess made by classifying the parked command string.
- The marker is read from the task file the resolver **already opens** to resolve the item's task name — no new source, no new stored field, nothing added to the item.
- The marker's **presence suppresses** the pair and its **absence renders** it exactly as today: an absent, unreadable or unparsable task file never removes a control, and the headless gate that decides whether the pair exists at all is unchanged.
- Every other card element — jump corner, corner X, provenance line, the `message` and `ack` controls — is unchanged.

## Problem

The board renders one-click **Allow / Deny** on a headless worker's `permission` card. A headless worker has no pane to answer in, so the board is the one place its gate can honestly be released — that is spec 004's shipped gate. But some of those parks are **irreversible**: a `make install`, a `launchctl kickstart`, a `kubectl apply`, a deploy. One click on Allow there launches a destructive action from a control the operator can hit by accident, with no confirmation step and no undo. The honest signal cannot be inferred from the parked command: commands obfuscate, alias, wrap in scripts and split across lines, so any classifier over the command string is either too weak to catch the destructive case or too broad to trust — and a classifier that fails **open** renders the one-click Allow on exactly the action this exclusion exists to prevent. The operator already records the fact that matters, by hand, on the task's own subtask line. That declaration is honest where a guess is not, and the resolver already reads the file it lives in.

## Goal

After this work, the board's Allow / Deny pair is **withheld** on a `permission` card whose item's task file declares a production-touching step, and renders **unchanged** on every other `permission` card — with the fact read from the task file the resolver already opens, present-suppresses / absent-renders, no new stored field on the item, and no other card element changed.

## Non-goals

- **Not a classifier over the parked command.** The exclusion is driven by the operator's declared marker, never by a pattern over the command, the tool name or the payload. Do NOT add a second, inferred signal beside the marker.
- **Not the tab-worker prohibition.** Spec 004's headless gate (`Provenance.Headless`) is unchanged; this work adds a term to the same condition and does not touch the term already there.
- **Not the release mechanism.** `armDelivery` in `bborbe/claude-supervisor`, which refuses a board answer with no `resolved_by`, is a separate task; this spec does not touch it and does not depend on it.
- **Not a new stored field.** Nothing is added to `Item`, to `PushRequest`, or to any producer. The fact is derived at page-render time from the vault, exactly as `Headless` is derived from the ledger.
- **Not `pkg/handler/attention-page.go`.** The row gate lands in `pkg/handler/attention-page-helpers.go`, where the `Decide` derivation already lives. The frozen file is not modified.
- **Not a config kill switch and not a per-item opt-out.** Do NOT add a flag that disables the exclusion or an override that forces the pair onto a marked card — the exclusion is the invariant; if a future consumer demands variation, that is a separate spec.
- **Not command-level matching.** The reading is task-level by design (see Desired Behavior 6); the refinement that matches the marker's command against the parked command is deliberately out of scope. Do not silently narrow or widen it.
- **Not the vault's marker convention, and not the vault's own files.** The `- [ ] ⚠️ production-touching — <command>` convention is read, never written, and the vault's task files are not edited by this work.
- **Not the `message` or `ack` controls, the jump corner, the corner X, or the provenance line.** None of them changes.

## Assumptions

- **The resolver already reads the task file's full content.** `taskIndex.addFile` reads each `25 Tasks/*.md` file whole (`os.Root.ReadFile`) to parse its frontmatter, its `goals:` list and its status, so the marker needs no additional read and no new directory scan.
- **The task index is built once, at construction, from `25 Tasks/*.md`, joined on the task's own `claude_session_id`.** The marker rides that same lookup and inherits its lifecycle: it is read when the vault is read, not per page load, exactly as the task name and its goal and topic already are.
- **The vault's marker convention is `- [ ] ⚠️ production-touching — <command>` on a task's own subtask line.** This is the operator's authored form, recorded in the operator's global guidance and present on this task itself. **It is documented in-tree at `docs/production-touching-marker.md`** so the board→vault dependency outlives this spec — the convention is not otherwise discoverable from this repository.
- **The board ships to one target** — the operator's own launchd service on `:18080` — so Rung-2 is this project's only verification rung.
- **No existing fixture carries the marker.** No file under `pkg/`, `e2e/` or `scenarios/` contains the phrase today, and the e2e harness configures no vault (so its task index is empty and the pair keeps rendering there), so this change requires no reconciliation of an existing permission-row test — unlike spec 004.

## Desired Behavior

1. A `permission` item whose session's task file declares a production-touching step renders **no answering control** — no `data-decision` button, no form and no input — while a `permission` item whose task file carries no such declaration renders the Allow / Deny pair exactly as it renders today.
2. The declaration is detected **only** in the list-item marker form: a line that is a task checkbox (`[ ]`, `[x]` or `[/]`) carrying the warning glyph and the phrase, followed by the em-dash separator — `^\s*-\s*\[[ x/]\]\s*(?:⚠️?)?\s*production-touching\s*—`. ⚠️ **The glyph group is `(?:⚠️?)?` and the outer group is load-bearing, not decoration:** `⚠️` is two code points (U+26A0 + U+FE0F), so a bare `⚠️?` makes only the *selector* optional and still requires the base glyph — it fails every marker written without one, the opposite of "the glyph is optional". ⚠️ **The state class must cover every checkbox state the vault writes, because a state the matcher misses leaves the pair rendering — the fail-open direction.** The phrase appearing in ordinary prose — in an Impact, Success Criteria or Progress section, or on a non-checkbox bullet — does **not** suppress the pair. The glyph is optional; the checkbox, the phrase and the em-dash are each required.
3. The fact is derived from the task file the resolver **already reads**, at index-build time, and surfaced on the item's provenance as a boolean. No new file is opened, no new directory is scanned, and nothing is stored on the item: the fact is a render-time derivation, exactly as the headless fact is.
4. The boolean is a **control gate, not a line fact**: it is deliberately NOT a member of `Provenance.Resolved()`. `Resolved()` gates whether the provenance `<div>` renders at all, and its members are the values that div *draws* — a boolean that draws nothing does not belong in it. ⚠️ **The rule is a contract, not a bug fix, and the shape it guards against is unreachable in this spec:** `taskIndex.addFile` returns early unless the task file carries a `claude_session_id`, and the resolver sets a non-empty `TaskName` whenever a task resolves, so the marker always co-occurs with a drawn fact and no marked card can render an empty provenance line. It is kept because it is the same rule the headless fact follows and because a later change could make the shape reachable — not because this change can produce it.
5. The exclusion is **fail-open for the marker and fail-closed for the control**: an absent, unreadable or unparsable task file, a task file whose session does not match, and an absent marker all leave the pair rendering exactly as it renders today, while the headless gate that decides whether the pair exists at all is unchanged and still fails closed. Every failure path in the marker read returns the empty answer and is logged at V(2)/V(3), the same soft-fail the other vault reads take — never an error that fails the page.
6. The reading is **task-level, not command-level**: any marker in the item's task suppresses the pair for every park that task raises. ⚠️ **Accepted trade-off, with its cost named:** for a task carrying an ops step, its other, benign parks also lose the control — and a headless worker has no pane to answer in, so those fall to the ~15-minute auto-deny. That is the fail-safe direction and it is the approved design; matching the marker's command against the parked command is deliberately out of scope (Non-goals).
7. Nothing else on the card changes: the jump corner and its jump command, the corner X, the state line, and the provenance line with its task, goal, topic, host, cwd, tool, pane and session-name spans all render on a marked row exactly as on an unmarked one.

## Constraints

- ⚠️ **`pkg/handler/attention-page.go` is frozen and must not be modified.** The row gate lands in `pkg/handler/attention-page-helpers.go`, at the `Decide` derivation, beside the headless term. The frozen file is not touched.
- ⚠️ **The Allow / Deny control's identity is frozen.** The pair is the existing `<div class="actions">` holding `<button type="button" class="dismiss" data-decision="deny">✕ Deny</button>` and `<button type="button" class="next" data-decision="allow">✓ Allow</button>`. AC1, AC2, AC3, AC4 and the `## Verification` probes key on `data-decision="allow"` and `data-decision="deny"`, so they are an interface rather than a style choice. No new element, class or marker is introduced.
- ⚠️ **The new fact must NOT join `Provenance.Resolved()`.** `Resolved()` gates whether the provenance `<div>` renders at all, and its members are the values that div *draws*; adding a boolean that draws nothing would put a non-drawing value in the line's gate. The new field is a control gate, not a line fact — the same rule the headless fact follows, and the reason `Headless` is likewise excluded. ⚠️ **Stated as a contract rather than a bug fix:** the empty-`<div>` shape is unreachable here (the marker only resolves from a task file that also sets a non-empty `TaskName`), so this constraint is a standing rule about what belongs in `Resolved()`, not a live defect it prevents. It is pinned by its own Acceptance Criterion, because no served-page probe can reach it.
- ⚠️ **The marker must be matched in the list-item marker form only, never as a bare substring.** A substring match on `production-touching` fires on ordinary prose — the vault's own task files discuss the term in their Impact, Success Criteria and Progress sections — and a false positive here removes a control the operator needs. The canonical form is `^\s*-\s*\[[ x/]\]\s*(?:⚠️?)?\s*production-touching\s*—`, with the checkbox state class covering every state the vault writes and the em-dash separator required. ⚠️ **The glyph group needs its outer `(?:…)?`:** `⚠️` is U+26A0 + U+FE0F, so `⚠️?` alone leaves the base glyph required.
- ⚠️ **Fail-open for the exclusion is the invariant, and the direction is not negotiable.** Any uncertainty about whether a task declares a production-touching step resolves to *not declared*, which renders the pair. The worst case of that direction is a pair on a park whose task did not declare one — never a missing pair on a park that did. This is the opposite polarity to the headless gate, whose uncertainty resolves to *no control*; both polarities are deliberate and neither may be flipped.
- ⚠️ **No new stored field and no producer change.** Nothing is added to `Item`, to `PushRequest`, or to any producer; the fact is derived from the vault at render time. A boolean carried on the resolver's own `Provenance` (and on the task it indexes) is a derivation, exactly as `Headless` is, not a stored field.
- **The marker rides the existing task-index read.** The whole `25 Tasks/*.md` file is already read whole at `taskIndex.addFile`; the marker is detected from that same content, so the change adds no `ReadFile`, no `ReadDir` and no new directory. The read stays confined beneath the tasks directory through the same `os.Root` handle, so a name taken from the directory listing can never walk out of it.
- **The task index's join and lifecycle are unchanged:** it is built once from `25 Tasks/*.md`, keyed on each task's own `claude_session_id`, with the existing tie-break between files sharing one session id. The marker rides that same lookup and is read when the vault is read, not per page load.
- **No existing test is reconciled by this change, and each keeps asserting what it exists for.** The permission-row cases in `pkg/handler/attention-page_test.go` use a mocked resolver whose `Provenance` carries a zero `ProductionTouching`, and the served-page cases in `pkg/handler/attention-headless-page_test.go` write a task file with frontmatter only; both therefore keep their pair. ⚠️ **No fixture under `pkg/`, `e2e/` or `scenarios/` may be given the marker form** — doing so would silently suppress a pair an existing case asserts.
- **Test types follow the repo's guide:** Ginkgo v2 + Gomega, external `_test` package, a real in-memory libkv DB rather than a mocked one, and counterfeiter mocks from `mocks/`. The served-page cases assert on the rendered row, scoped per item id, never page-wide.
- Errors wrap with `github.com/bborbe/errors`; no `fmt.Errorf`, no bare `return err`.

## Security / Abuse Cases

The change adds no route, no input, no credential and no file write. It adds **no read either** — it detects one marker in a task file the resolver already opens whole — and gates one existing control on it.

- **What crosses a trust boundary:** the join key — the item's session id, recovered from the producer-claimed `LivenessRef`. ⚠️ **This is the existing trust model, not a new one:** the same producer-claimed id already keys the pane, task and session-name joins, and a producer that names another session's id already inherits that session's task name, goal and topic. A producer that names a session whose task carries the marker loses the pair — the fail-safe direction; a producer that wants the pair must name a session whose task carries none, which is the same claim the headless gate already rests on. This work neither widens nor narrows that boundary.
- **What must be validated:** nothing new is interpolated into the page — the new fact is a boolean that selects which existing controls render, and the marker text never reaches the document. The task file is read whole through the existing `os.Root` handle, so a crafted file name from the directory listing cannot walk the read out of the tasks directory, and the item's session id is used only as a map key, never as a path segment.
- **What can hang or exhaust:** nothing new. The marker is scanned from content already held in memory during the index build; no file is opened, no directory scanned, and no subprocess runs. A page load does not re-read the vault.
- **What must fail safe:** every unreadable, missing or unrecognised input resolves to *not declared*, which renders the pair — the direction whose worst case is a missing exclusion on a park that did not declare one, never a missing control on a park that did.

⚠️ **Size budget, stated rather than left to a re-derivation:** 7 Desired Behaviors × 8 Acceptance Criteria = **56**, marginally over the advisory signal of 50. **The spec is deliberately not split.** That signal reads "the spec is multiplying its own surface", and the test for it is whether natural seams exist — here there is exactly one (detect the fact, then gate on it), it is already the two-prompt decomposition above, and the ACs are wide rather than deep: four of the eight are one served-page probe asserting different input shapes, and two more are the standard build-gate and CHANGELOG items every spec in this repo carries. Splitting would produce two specs that cannot be verified apart. ⚠️ **The eighth AC was added by audit, not by scope growth** — the `Resolved()` rule had no criterion reaching it, so a build could under-implement it and pass everything else.

## Do-Nothing Option

The board keeps rendering a one-click Allow on a headless worker's production-touching park. The operator's only guard is reading the command on the card, and one click on a `make install` or a `launchctl kickstart` launches an irreversible action with no confirmation and no undo. The cost is paid on every such park, and the fact that would prevent it — the operator's own declaration on the task — is already written down and already read by the resolver. This change turns that declaration into the board's own guard.
